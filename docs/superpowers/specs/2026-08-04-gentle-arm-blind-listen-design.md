## 3. Workload

**Eight pairs** (raised from five at the owner's pre-run review, 2026-08-04, accepting
the larger listening spend). Endpoints drawn from the owner's familiarity — his Spotify export
(streaming history play counts, `YourLibrary.json`, `Follow.json`) proposes candidates;
he approves or amends. (Correction at plan time, 2026-08-04: the export's
`Follow.json` holds followed *users*, not artists, and contributes nothing — the
familiarity sources are the streaming history and `YourLibrary.json`.) Constraints:

- Every endpoint must resolve in **both** graphs (the candidate map lacks roughly a third
  of production artists); feasibility is checked before the list is fixed.
- Familiar↔familiar dominates the set — REQ-41 makes unfamiliar territory uninformative,
  and familiar pairs are the defect's home territory. One cross-genre pair for a long
  journey, feasibility allowing.
- **The approved pair list is committed as `GBL-AM1` to this file's §8 before any journey
  is generated.** The raw Spotify export never enters the repo; only the derived,
  approved pairs do, with their MBIDs.

**Bypass policy: the measured object, unchanged.** The all-`known` ladder exactly as the
experiment pressed it — same target-selection rule, cited to `cre_ladder.py`, pinned by
the execution plan. No new policy is invented for the listen; the ear judges the thing
the numbers describe.

**Depths: d0, d10, d20** per pair per arm. The measured effect lives at depth ≥ 10
(`CRE-C1`'s territory); d0 is an **anchor row** — first paths are expected to be broadly
similar in character, and a large d0 difference is itself informative (it is the cost of
the graph swap alone, before the ramp does anything). Three depths rather than C3's four
keep eight pairs to roughly five hours, splittable across sittings; a partial sitting is
fine, but no read exists until all eight pairs are done (§5's run state).

## 4. What the listener sees

A side-by-side page per pair, C3 format:

- Both arms' journeys at d0 / d10 / d20, **depth order preserved within an arm**
  (the judgement is how the journey evolves with presses), arm tokens (left/right)
  **shuffled per pair**, no labels, no metrics.
- 30-second clips per card, resolved through the app's own resolver path for both arms.
  `BYP-13` (wrong-artist clips) is live in both arms and shared machinery: **ignore clip
  failures unless they differ by arm** (C3 §8 rule).
- Per depth row: pick **left / right / no preference**, plus two fixed plain-language
  claims answered per pair at the end — **one per assessment axis, deliberately
  separated** so a side that wins one axis and loses the other can be recorded honestly
  (owner's review note, 2026-08-04). Wording frozen now:
  - `GBL-Q1` — **novelty**: *"As the presses accumulate, which side, if either, delivers
    more artists new to you?"*
  - `GBL-Q2` — **coherence**: *"Which side, if either, holds together better as a
    journey — each step a sensible next listen? Did either side collapse into a random
    walk into obscurity?"* (the collapse clause is the failure mode the strong arm made
    plausible; asked of the gentle arm deliberately)
- Free-text notes per row — the §3.9 corpus is the most operationally useful artifact the
  last listen produced; this one should add to it.

## 5. Reads — fixed in advance, with the branch's effect size

**Primary read: the 16 deep rows** (8 pairs × d10, d20). **A "clear pick" is a
left/right choice on a single deep row** — each pair contributes two rows to the tally,
and a "no preference" row counts for neither side. The d0 rows never enter the tally
(they are the §5 anchor, reported separately). Margin ≥ 5 clear picks — (winning side's
rows) − (other side's rows) ≥ 5, so 9–4 with three no-preferences fires and 10–6 does
not — is the branch trigger. Below 5, across 16 rows, this instrument cannot tell
preference from noise, and the read is the null. (The margin scales the approved 3-of-10
bar proportionally to the larger workload — 16 × 0.3 = 4.8, rounded **up**, so the
enlarged listen cannot fire on a proportionally weaker signal. Fixed at the owner's
pre-run review, 2026-08-04; no journey existed at the time.)

**Run state every read presupposes:** all 8 pairs × 3 depths × both arms generated,
presented, and verdict rows recorded. A partial run licenses **no read**; what is owed is
named and the listen resumes or is abandoned by the owner, not summarized.

**The test runs once.** An unwelcome verdict stands; re-testing it is forbidden. Same
scope as the Phase 2 §15 rule as bounded by the owner 2026-07-23: this binds *this
verdict* — new candidates on new findings may still be listened to.

**The d0 anchor is not in the primary read.** It is recorded and reported; if d0 alone
shows a strong V0 preference, that is a finding about the graph swap's up-front cost,
reported alongside whatever the primary read says — it does not veto or rescue either.

## 6. Blind protocol

- **Sealed mapping.** Arm→token assignment per pair is generated by script, written to a
  gitignored file under `.superpowers/` (the `BLIND-MAPPING.json` convention) **before**
  serving, and read by no one until every verdict row is on disk.
- **The runner session is fresh and mechanics-only.** It executes generation and serving
  from a brief that contains no results, no expected outcome, and no framing. It does not
  read `findings/2026-08-04-cap-reevaluation-results.md`, NEXT.md's result paragraphs, or
  §1–§2 of this file, and it says nothing to the owner beyond mechanics
  (CLAUDE.md, "Exception — blind evaluations"). This planning session does not run the
  test (it knows the results; Phase 2 §15 "Session hygiene" precedent).
- **No Spotify monthly-listeners during the listen** (WGLL bound; one comparison in the
  record was already voided for an information leak). After the verdict is recorded, the
  instrument is available as usual, and any check that changes a mind gets written down.
- **The blind is imperfect, disclosed now.** The arms differ in graph and behavior; the G
  side may become guessable at depth. Accepted in advance, as §15 accepted the same for
  `d025`/`capfix`. Per-pair token shuffling is the mitigation.
- **Differential check before handover** (§16 precedent): one query must return different
  journeys across the two arms, proving the page is not serving one artifact against
  itself.
